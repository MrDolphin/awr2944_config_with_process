## 已验证的 AWR2944P 拓扑

```text
AWR2944P XDS110 USB ──> Raspberry Pi USB
  /dev/ttyACM0          AWR2944P CLI
  /dev/ttyACM1          auxiliary UART（暂不参与控制）

DCA1000 Ethernet ─────> Raspberry Pi eth0
  Pi eth0               192.168.33.30/24
  DCA1000 FPGA          192.168.33.180
  DCA control           UDP 4096
  DCA raw data          UDP 4098
```

DCA1000 已实测 ARP MAC：`0c:22:38:4e:5a:0c`。

`eth0` 是 DCA 专用网络。不要以 Wi-Fi 切换、默认路由试验或 NetworkManager Wi-Fi 操作修改该接口。

## AWR2944P 可复制操作

### DCA 就绪检查与配置

```bash
ip -br addr
ip route
ip neigh show dev eth0

cd ~/awr2944_config_with_process_github
source .venv/bin/activate
python tools/dca1000_configure.py \
  --dca-ip 192.168.33.180 \
  --system-ip 192.168.33.30 \
  --mac 12.34.56.78.90.12 \
  --packet-delay-us 25 \
  --timeout 5 \
  --apply
```

正确证据是每条命令收到 `192.168.33.180:1024` 应答且 `status_hex` 为 `00 00`。DCA1000 的 ping 不稳定，不能用 ICMP 成功/失败替代 UDP 4096 验证。

### 短采集与分析

先确认 `eth0` 保持 `192.168.33.30/24`，再执行：

```bash
cd ~/awr2944_config_with_process_github
source .venv/bin/activate
python tools/awr2944_capture_once.py \
  --duration 20 \
  --analyze-range \
  --post-analyze
```

临时替换时长或输出目录：

```bash
python tools/awr2944_capture_once.py \
  --duration 60 \
  --output-dir /home/pi/radar_runs/target_5m \
  --analyze-range \
  --post-analyze
```

成功日志至少包含：

```text
[UDP] Listening on 192.168.33.30:4098, SO_RCVBUF=128.0 MB
[CAP] ... drops=0
[DONE] Saved ...
[RANGE-ANALYSIS] ...
[POST-ANALYSIS] capture_integrity=PASS ...
```

曾见 `record_start: no response; continuing` / `record_stop: no response; continuing`。若 UDP 4098 有连续数据、`.bin` 非零、`drops=0`，则本次原始数据通路有效。

## 当前数据证明了什么，没证明什么

已证明：

1. DCA1000 UDP 接收、序号连续性、`.bin` 容器写入可用，存在 `drops=0` 的成功采集。
2. 16-bit 字统计正常，没有满量程饱和证据。
3. 当前候选格式可重组出候选帧，并能输出时域、1D FFT、range-time、**诊断性** 2D 图。

尚未证明：

1. 绝对距离标定。
2. RX/TX 相位标定。
3. 可信多 TX TDM 慢时间排序，因此当前 RD 不可作为可发布速度结论。
4. AoA、点云精度、海杂波统计结论。

5 m 角反射器测试中，候选峰约 `5.055 m`、相对约 `-20.90 dB`，而最强稳定峰约 `8.192 m`。可能是环境反射或多径，不能直接当作 range bias。下一步应做放入/移除/移动或转动角反的 A/B 试验，确认峰随已知目标移动后才进入标定。

## AWR2243（假设 AWR2243BOOST + DCA1000）适配路线

### 不能直接复用 AWR2944P 的部分

AWR2243 是 sensor-only 器件，没有 AWR2944P 的 `mmwDemo` CLI / UART 控制模式：

```text
不要把 Config/test_full.cfg 发到 AWR2243。
不要用 awr2944_cli_control.py 控制 AWR2243。
不要假定 AWR2944P real-only / 2-lane 解码规则适用于 AWR2243。
```

AWR2243 独立控制需要 TI DFP / mmWaveLink host：SPI mode 0、16-bit word、每 word CS、IRQ、nRESET、SOP。Linux 没有完整等价 mmWave Studio GUI；先做 Windows baseline，Pi 独立控制最后做。

### 已有但未实测的资料

```text
Config/交接文档/scripts/22xx.setup.json
Config/交接文档/scripts/22xx_vitalsign_highSNR.json
Config/交接文档/mmWaveStudio数据采集交接文档.md
```

其中 profile 看起来是近距 vital-sign 候选而非海面/长距 profile：4 RX / TX0、1024 samples、12 MSps、40 MHz/us、1 chirp/frame、50 ms frame period、`numFrames=2400`、`laneEn=0xF`（4 lane）、600 Mbps。必须由一次实际 Studio 采集的配置、DCA 日志、`.bin` 字节数、已知目标试验重新验证。

### 实施阶段门

1. **Windows baseline**：按现有 AWR2243 Studio profile 完成稳定 DCA1000 采集；保存 JSON/Lua、DCA 设置、Studio 日志、`.bin`、字节数、真实场景说明。
2. **离线 decode**：写 AWR2243 专属 decoder/analyzer；先根据文件长度验证 4-lane、real/complex、I/Q/lane/order，不输出 AoA。
3. **Pi DCA 数据面复用**：只复用通用 UDP 接收层，在元数据中增加 profile-aware 格式合同，不能沿用 AWR2944P 假设。
4. **Pi 独立控制**：最后基于 TI DFP C host application / mmWaveLink 在 Pi 编译，通过 subprocess wrapper 调用。先用 Pi USB→DCA J1 FTDI + AWR2243 XDS J8 建立等效控制链；直接 Pi GPIO SPI/IRQ/reset 属于后续阶段。

### 硬件前置条件

DCA1000 断电后再改拨码。AWR2243 4-lane 采集需要 `SW2.3` 在 `1243_MODE` 一侧；不能与当前 AWR2944P 的实际 lane 方案混用。AWR2243BOOST 的 SPI/CAN selector 应为 SPI。
